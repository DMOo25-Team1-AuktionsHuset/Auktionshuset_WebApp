# Device gateway SignalR client

The API owns one hosted client, disabled unless `DeviceGateway:HubUrl` is configured. Set it to the exact dedicated hub URL, e.g. `https://localhost:5001/hubs/device-gateway`, with a trusted certificate. HTTPS is required; HTTP loopback is allowed only in Development with `DeviceGateway:AllowInsecureLoopback=true`. Credentials, query strings, fragments, other paths and automatic redirects are rejected. The client uses WebSockets without SignalR negotiation; deployments must support WebSockets and direct connections, not a negotiation-redirect service or transport fallback.

The client issues a new five-minute JWT whenever SignalR requests a token, including on reconnect, using `DeviceGateway:Authentication:SigningKey`, `Issuer` and `Audience` and the `device.gateway` scope. The key must be at least 32 UTF-8 bytes and distinct from `Authentication:SigningKey`; protect it in a secret store. Signing-key possession grants gateway-token minting authority. WebSocket authentication can place the token in the `access_token` query parameter; configure servers and proxies to redact query strings from access logs. The previous `DeviceGateway:AccessToken` setting is incompatible and is rejected when the client is enabled. The hub closes connections at token expiration, after which the client reconnects and resynchronizes.

The client subscribes to the existing `IDeviceGatewayClient` methods: `AuctionChanged(Guid eventId, Guid auctionId, long auctionRevision)` and `AssignmentChanged(Guid eventId, Guid deviceId, Guid sessionId)`. The hub must deliver all relevant notifications from connection establishment; if subscriptions are introduced, they must be restored before fetching snapshots.

An authenticated device transport creates a `DeviceSnapshotConnection` with the authenticated device and session IDs, the singleton processor and `IDeviceCurrentStateReader`, and its own `IDeviceSnapshotSink`. Call `RegisterAsync` and `Unregister` on disconnect. Registration and invalidations fetch a fresh session-scoped database snapshot; reconnect invokes the same refresh. An invalid session invokes `SetReleasedAsync` and unregisters the connection. Snapshot amounts are decimal kroner; the transport must convert them exactly to integer øre. The sink must start unavailable and must not permit bids unless `DeviceGatewayProcessor.IsConnected` and its authoritative snapshot are both valid. Snapshot callbacks are serialized; old auction revisions are ignored and newer revisions cause a full refresh, not reconstruction of intermediate events. The registry is not an authenticated device transport.

The client retries initial connection and later disconnects every five seconds. After each successful start it asks every currently registered device to resynchronize, holding incoming notifications until those calls finish. A connection, snapshot or notification failure causes devices to be marked unavailable and a fresh connection and resync to be attempted. Device callbacks must honor cancellation and must not block indefinitely. A failed unavailable callback is logged; the client cannot enforce bid gating inside an independent device implementation.

A focused loopback test exercises the real authenticated hub, forwarding and reconnect following a device callback failure. Snapshot projection has SQLite coverage; PostgreSQL and end-to-end snapshot delivery require an isolated PostgreSQL server and a device transport. Production TLS behavior, token-expiration timing and registration-race safety remain unverified.
