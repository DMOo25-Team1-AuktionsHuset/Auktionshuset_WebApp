# Start prices and stock rollout

- Each auction line sells all its units to one winner. StartingPrice and bid Amount are totals for that line; neither is multiplied by Quantity. Existing prices and quantities are preserved with this meaning, without guessing earlier intent.
- Prices use the existing numeric(18,2) column. Starting price 0 is valid; negative, oversized and fractional-cent amounts are rejected without rounding. Bids must additionally be positive. An omitted price means 0 for a new line and preserves the stored price for an existing line.
- Lot.Quantity is the authoritative physical stock baseline at rollout. Open lines on stored Kommende/Live auctions reserve stock, even after the planned end. Editing replaces only that auction's reservations; deleting an upcoming auction releases them. Closing an unsold line releases its reservation; closing a sold line debits its complete quantity and releases its reservation in the same transaction as winner, close marker and outbox. ClosedAtTime prevents repeat debit, including concurrent closes.
- No migration is required: existing auction lines and close markers contain the reservation and idempotency state. Historical closed sales are NOT retroactively debited: there is no reliable evidence in the schema that distinguishes a previously manually adjusted stock count. Review the historical-sale output against physical inventory before rollout and make explicit, reviewed corrections separately.
- Run scripts/audit-auction-stock.sql read-only against the intended database before rollout. Reconcile over-reservations, invalid amounts/counts, unknown statuses and inconsistent lifecycle markers explicitly. Do not change counts, scale prices, convert statuses or replay closes automatically. Starting conflicting auctions is blocked, and selling cannot reduce stock below other active reservations. Upcoming auctions can be reduced/deleted to resolve over-reservations; unsold closing releases stock.
- Stock decisions use PostgreSQL transaction advisory lock 704291031, acquired before auction row locks. This deliberately serializes auction writes and warehouse quantity updates across processes. Normal application handlers must use the shared write session; direct SQL/imports bypass it and need the same lock and validation. A narrower per-stock locking scheme is a separate scaling change.
- No existing application database was connected/audited during this task. Only isolated PostgreSQL 16 test databases were used. Run the audit on the deployment database to establish concrete data issues.

## PostgreSQL regression tests

Set AUCTION_STOCK_TEST_CONNECTION to an isolated PostgreSQL server where the test user can create databases, then run `dotnet test Auktionshuset.Api.Test --no-restore --filter FullyQualifiedName~AuctionStockPostgresTests`. Each test creates a generated codex_stock_* database and drops only that database. The tests skip explicitly when this variable is absent; no runtime connection strings are used implicitly.
